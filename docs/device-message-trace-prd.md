# 小勾臂箱报文｜产品需求说明

本说明已同步展示在“箱体监控 → 小勾臂箱报文”页面顶部的可折叠产品需求面板中。当前页面是模拟数据原型，没有接入实时设备或持久化服务。

## 1. 业务目标

产品、研发和运维按三位箱号（001—370）、设备号、平台时间查看原始上下行报文、解析后的传感器数据、平台操作和设备应答。通过相邻记录判断满溢率短时跳变，通过请求、下发、应答的时间判断指令延迟发生在哪个阶段。

## 2. 行业参考与本项目原则

本项目采用三条可复盘的链路：

1. **原始消息可追溯**：完整保留上下行帧、平台收发时间、校验结果及解析错误。解析失败也不能丢弃原帧。
2. **设备状态可查询**：保留电压、温度等原值及单位，同时保存距离、满溢率等换算值、告警状态、公式和箱体参数版本。历史结果可按当时规则复现。
3. **命令执行可关联**：为一次远程操作分配内部唯一指令 ID，关联用户请求、每次发送尝试、设备应答；若后续协议提供继电器状态，再补充其状态变化；分别记录结果及时间。

[AWS IoT Commands 官方文档](https://docs.aws.amazon.com/iot/latest/developerguide/iot-remote-command-concepts.html)采用唯一执行 ID，并跟踪 CREATED、IN_PROGRESS、SUCCEEDED、FAILED、REJECTED、TIMED_OUT 等执行状态。[AWS IoT Device Shadow 官方文档](https://docs.aws.amazon.com/iot/latest/developerguide/device-shadow-document.html)用 clientToken 关联请求与响应，并区分期望状态与设备上报状态。本项目借鉴关联和状态管理方法；设备通信仍按 JT/T 808 及硬件扩展协议实现，不直接依赖 AWS IoT。

终端 `0x0001` 对 `0x8500` 返回成功，只能证明协议应答成功。现有模拟协议的 E7 标为 RFID 门状态，不能证明继电器是否上电；目前只显示协议应答，不推断继电器动作。硬件方若提供明确的继电器反馈，才增加实际状态。

## 3. 页面需求

| 模块 | 功能 | 验收要点 |
| --- | --- | --- |
| 查询 | 输入箱号、设备号，选择事件类型和平台时间范围，并输入温度下限、电量上限或刷卡卡号 | 箱号和设备号支持部分匹配，事件类型按分类筛选；温度按换算摄氏度严格大于、电量按换算百分比严格小于、卡号按文本部分匹配；条件可组合，未携带相应字段的报文不命中该条件；正式版限制最大跨度并分页 |
| 列表 | 按平台时间倒序，混合显示平台操作、上行和下行报文 | 红外电压／距离／满溢率、电池电压／电量、温度原值／换算、卡号／刷卡时间分别按组展示；另显示设备上报时间；经纬度列仅显示“查看”，点击后按报文坐标逆地理编码并显示地址，失败时保留坐标和错误；关联指令、CSQ、卫星数和定位状态保留在详情；不适用字段显示“—” |
| 详情 | 完整 HEX、协议版本、消息体声明及实际长度、校验、解析字段、设备时间、平台时间、流水号、关联指令；高程、速度、方向、报警及状态标志、E7 原值 | 解析失败仍展示原始帧和错误原因；敏感字段按权限脱敏 |

满溢排障以相邻上报记录的“红外电压 → 距离 → 瞬时满溢率 → 告警结果”为主。瞬时越线和正式告警必须分别展示，不以一次越线直接认定持续满溢。

开锁排障以同一时间线中的平台请求、下行 `0x8500`、上行 `0x0001` 为主；据其平台时间计算请求至下发、下发至应答的耗时。当前协议没有已确认的继电器反馈，不推断实际动作时间。

另需支持心跳（0x0002）、注销（0x0003）、注册（0x0100）、鉴权（0x0102）、平台通用应答（0x8001）、注册应答（0x8100）与参数设置（0x8103）的查询；鉴权码在解析字段和 HEX 中脱敏。模拟文档中的 0x8103 长度与校验均异常，应保留原帧并显示解析错误。

事件类型仅用于查询分组；注册与注册应答等消息是否合并展示，由技术方案根据协议关联能力确定。

## 4. 数据模型与关联

- `iot_message`：设备号、方向、消息 ID、流水号、平台收发时间、完整帧、校验状态、解析状态及错误。
- `iot_message_parse`：关联原始帧，保存设备时间、箱号、原始传感器值及单位、换算值、卡号、协议扩展字段、解析器和公式版本。按历史绑定关系确定箱号。
- `iot_command`：内部指令 ID、操作人、目标、动作、请求时间、发送时间、对应下行报文及流水号、应答报文与结果、超时原因；若有可靠继电器反馈再记录状态变化报文与时间。重试需保留每次发送尝试。

`0x0001` 与下行 `0x8500` 通过设备号＋应答消息 ID＋应答流水号，在限定会话和时间窗口内关联；业务层统一使用内部 `command_id`。应处理流水号循环、重复帧、乱序及超时。平台时间和设备时间分别保存，入库统一 UTC，界面按时区显示；设备时钟漂移不可覆盖平台时间。

## 5. 性能、安全与待确认

按设备号、箱号及平台时间建索引。查询限制时间跨度并分页；原始帧留存期、归档策略按设备频率和运营需求确定。鉴权码和卡号按角色授权与脱敏；常规列表不显示鉴权码。

上线前需由硬件方确认红外、电池、温度的单位和换算公式，`E7` 字段实际含义及 `0x8500/0x0001` 的实际语义、是否有动作完成回报、告警判定规则及指令超时策略。现有模拟文档的 `0x8103` 样例消息体长度与校验不一致，不能作为验收帧。
