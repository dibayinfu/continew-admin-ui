# 小勾臂箱报文｜产品需求说明

本说明已同步展示在“箱体监控 → 小勾臂箱报文”页面顶部的可折叠产品需求面板中。当前页面是模拟数据原型，没有接入实时设备或持久化服务。

## 1. 业务目标

产品、研发和运维按三位箱号（001—370）、设备号、平台时间查看原始上下行报文、解析后的传感器数据、平台操作和设备应答。通过相邻记录判断满溢率短时跳变，通过请求、下发、应答的时间判断指令延迟发生在哪个阶段。

## 2. 行业参考与本项目原则

本项目采用三条可复盘的链路：

1. **原始消息可追溯**：完整保留上下行帧、平台收发时间、校验结果及解析错误。解析失败也不能丢弃原帧。
2. **设备状态可查询**：保留电压、温度等原值及单位，同时保存距离、满溢率等换算值、公式和箱体参数版本。历史结果可按当时规则复现。
3. **命令执行可关联**：为一次远程操作分配内部唯一指令 ID，关联用户请求、每次发送尝试、设备应答；若后续协议提供继电器状态，再补充其状态变化；分别记录结果及时间。

[AWS IoT Commands 官方文档](https://docs.aws.amazon.com/iot/latest/developerguide/iot-remote-command-concepts.html)采用唯一执行 ID，并跟踪 CREATED、IN_PROGRESS、SUCCEEDED、FAILED、REJECTED、TIMED_OUT 等执行状态。[AWS IoT Device Shadow 官方文档](https://docs.aws.amazon.com/iot/latest/developerguide/device-shadow-document.html)用 clientToken 关联请求与响应，并区分期望状态与设备上报状态。本项目借鉴关联和状态管理方法；设备通信仍按 JT/T 808 及硬件扩展协议实现，不直接依赖 AWS IoT。

终端 `0x0001` 对 `0x8500` 返回成功，只能证明协议应答成功。扩展字段 E7 作为 RFID门状态展示：1 表示通电，0 表示未通电。

## 3. 页面需求

页面先展示页签，再在各页签内展示对应查询条件：

1. **设备报文**：展示状态上报和刷卡事件，并可按这两种事件筛选。按平台时间倒序，显示设备时间、红外／距离／满溢率、电池电压／电量、温度、卡号／刷卡时间及地址查看入口。箱号、设备号、平台时间、温度下限、电量上限和卡号可组合查询。
2. **远程控制**：按一次控制任务聚合展示。每行记录平台操作时间、下发指令时间、应答时间、操作人、动作和应答结果。应答结果字段只允许成功、失败；尚未收到应答时数据库为空，页面显示“—”。点击下发或应答时间可查看对应原始报文。

“设备报文”的查询条件为箱号、设备号、事件（状态上报／刷卡事件）、温度下限、电量上限、卡号和平台时间；“远程控制”的查询条件仅为箱号、设备号和平台时间。“连接与配置”不在本页面展示。注册、心跳、鉴权、注销和参数设置等消息若后续需要排查，应由技术方案确定单独入口。

设备报文排障以相邻上报记录的“红外电压 → 距离 → 瞬时满溢率 → 告警结果”为主。瞬时越线和正式告警分别展示，不以一次越线直接认定持续满溢。经纬度列仅显示“查看”，点击后按报文坐标逆地理编码并显示地址；关联指令、CSQ、卫星数、高程、速度、方向和协议头字段保留在详情。

远程控制以平台请求、下行 `0x8500`、上行 `0x0001` 组成一次任务。终端应答仅代表协议应答，不推断继电器实际动作时间。业务指令尚未下发时，下发指令时间为空；尚未收到应答时，应答时间和应答结果均为空。页面统一用“—”展示空值，不增加待下发、待应答或超时状态。

## 4. 数据模型与关联

- `iot_message`：设备号、方向、消息 ID、流水号、平台收发时间、完整帧、校验状态、解析状态及错误。
- `iot_message_parse`：关联原始帧，保存设备时间、箱号、原始传感器值及单位、换算值、卡号、协议扩展字段、解析器和公式版本。按历史绑定关系确定箱号。
- `iot_command`：内部指令 ID、操作人、目标、动作、请求时间、发送时间、对应下行报文及流水号、应答报文与结果；应答结果为空或取 SUCCESS、FAILED。重试需保留每次发送尝试。

`0x0001` 与下行 `0x8500` 通过设备号＋应答消息 ID＋应答流水号，在限定会话和时间窗口内关联；业务层统一使用内部 `command_id`。应处理流水号循环、重复帧、乱序及超时。平台时间和设备时间分别保存，入库统一 UTC，界面按时区显示；设备时钟漂移不可覆盖平台时间。

### 4.1 重点：连续指令与乱序应答的关联规则

> **这是远程控制链路的核心实现规则。** 连续下发多条远程开锁指令时，每次下发必须使用不同的 JT/T 808 消息流水号。平台必须在发送报文前，持久化 `command_id` 与设备号、下行消息 ID、下行流水号的映射。

终端返回 `0x0001` 通用应答时，应答消息体包含“应答流水号、应答消息 ID、结果”。其中应答流水号和应答消息 ID 共同指向原下行 `0x8500`；`0x0001` 报文头自身的流水号只标识本条上行应答，不能用于关联原指令。平台按以下关联键查找发送记录：

`设备号 + 应答消息 ID + 应答流水号`

例如连续点击三次远程开锁，平台依次分配下行流水号 `0042`、`0043`、`0044`。即使终端 30 秒后按 `0044`、`0042`、`0043` 的顺序返回，平台仍根据各应答消息体中的原下行流水号，将三条应答分别归入对应的 `command_id`，不依赖应答到达顺序。

实现时同时遵守以下规则：

1. 下行流水号按设备维度分配；同一设备的在途指令不得使用相同流水号。
2. 映射关系必须先入库再发送，避免应答先到而发送记录尚未落库。
3. 同一关联键收到重复应答时幂等处理：控制任务只采纳首次有效结果，同时保留重复原始帧供排查。
4. JT/T 808 流水号为 16 位循环值，匹配时需限定当前设备连接会话和合理时间窗口，避免回绕后误关联历史指令。
5. 若设备没有回传原下行流水号，或多条应答错误地回传同一流水号，平台无法可靠判断对应关系。此类记录标记为协议异常并保留原始报文，由设备固件修正，不能按到达顺序猜测关联。

## 5. 性能、安全与待确认

按设备号、箱号及平台时间建索引。查询限制时间跨度并分页；原始帧留存期、归档策略按设备频率和运营需求确定。鉴权码和卡号按角色授权与脱敏；常规列表不显示鉴权码。

上线前需由硬件方确认红外、电池、温度的单位和换算公式，`0x8500/0x0001` 的实际语义、是否有动作完成回报、告警判定规则及指令超时策略。现有模拟文档的 `0x8103` 样例消息体长度与校验不一致，不能作为验收帧。
